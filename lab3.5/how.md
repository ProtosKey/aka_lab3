# linear_filter на VLIW-IV: разбор решения

## Что вычисляем

Цифровой КИХ-фильтр второго порядка с фиксированными коэффициентами:

```
Y[i] = 3·X[i] + 2·X[i−1] + X[i−2]
```

где `X[−1] = X[−2] = 0`. Вход: N, затем N значений X[i] — всё через IO-порт 0x80. Выход: N значений Y[i] в IO-порт 0x84.

## Особенности VLIW-IV, которые определяют решение

Каждый **бандл** — это 4 слота, исполняемых параллельно:

```
[ALU1: 32 бит] / [ALU2: 32 бит] / [MEM: 24 бит] / [CTRL: 24 бит]
```

Ключевые правила:
1. **Все источники читаются до записей.** Если в одном бандле ALU1 пишет `t1`, а CTRL читает `t1` — CTRL видит *старое* значение. Это делает невозможным «написал и сразу проверил» в одном бандле.
2. **CTRL слот исполняется последним**, но записи всех слотов фиксируются до старта следующего бандла.
3. **Слоты независимы по назначению**: умножение только в ALU, загрузка/запись только в MEM, ветвления только в CTRL.

## Граф зависимостей одной итерации

Вычислить `Y[i]` нужно из трёх слагаемых. Распишем цепочку зависимостей:

```
                    ┌── lw t0 = X[i]  (MEM)
                    │
X[i]   ──────────► mul t1 = 3·t0    (ALU1)  ─────────────────► add t1 = t1 + t3  (ALU1)
                                                                         │
X[i−1] (= s2) ──► mul t2 = 2·s2    (ALU2)  ─┐                          │
                                              └► add t3 = t2 + s3 (ALU2)─┘
X[i−2] (= s3) ───────────────────────────────┘
```

Два наблюдения:
- `mul t2 = 2·s2` **не зависит** от свежего `t0` — его можно запустить **параллельно с `lw t0`**.
- `add t3 = t2 + s3` **не зависит** от `mul t1` — их можно запустить **в одном бандле**.

Это даёт **цепочку из 4 бандлов**:

| Бандл | ALU1 | ALU2 | MEM | CTRL |
|-------|------|------|-----|------|
| 1 | `nop` | `mul t2 = 2·s2` | `lw t0 = X[i]` | `nop` |
| 2 | `mul t1 = 3·t0` | `add t3 = t2 + s3` | `nop` | `nop` |
| 3 | `add t1 = t1 + t3` | `nop` | `nop` | `nop` |
| 4 | `mv s3, s2` | `mv s2, t0` | `sw t1, 0(s5)` | `jr ra` |

Бандл 4 — **100% загрузка** всех 4 слотов: одновременно сдвигается история (`s3←s2`, `s2←X[i]`), пишется результат (`sw`) и происходит возврат (`jr ra`). Это возможно потому, что все чтения (`s2`, `t0`, `t1`, `ra`) происходят до записей — сдвиг `s2`→`s3` при одновременной записи `t0`→`s2` корректен без временного регистра.

### Почему бандл 3 нельзя устранить

`add t1 = t1 + t3` читает `t1` (из бандла 2) и `t3` (из бандла 2). Оба записаны в бандле 2, значит прочитать их можно не раньше бандла 3. Перенести в бандл 2 нельзя — это создало бы RAW-конфликт внутри бандла.

## Структура процедур и стек

```
_start
  └─► run_filter      (jal ra → сохраняет ra на стек)
        └─► compute_y (jal ra → ra перезаписывается; compute_y — лист)
```

`run_filter` — **не лист**: перед первым `jal ra, compute_y` он сохраняет `ra` на стек, потому что иначе адрес возврата в `_start` был бы затёрт. Стековый фрейм — ровно 4 байта (одно слово).

`compute_y` — **лист**: ни одного вызова внутри, `ra` не трогает, стековый фрейм не нужен.

### Инициализация глобального состояния в _start

Все «глобальные» константы загружаются один раз в _start и хранятся в S-регистрах на протяжении всего выполнения:

```
s4 = 0x80   (адрес входного порта)
s5 = 0x84   (адрес выходного порта)
s6 = 3      (коэффициент для X[i])
s7 = 2      (коэффициент для X[i−1])
```

Это позволяет избежать повторной загрузки в каждой итерации и оставляет слоты свободными для полезной работы.

## Как работает счётчик цикла

```asm
rf_loop:
    addi s1, s1, -1  / nop / nop / jal ra, compute_y
    nop              / nop / nop / bnez s1, rf_loop
```

Декремент `s1` происходит **в том же бандле**, что и `jal`. Это не конфликт: `jal` читает `pc` (не `s1`), а запись `s1` происходит до старта `compute_y`. Когда `compute_y` возвращается через `jr ra`, следующим бандлом является `bnez s1, rf_loop` — к этому моменту `s1` уже уменьшен. Таким образом цикл из N итераций выполняется за **2 бандла на итерацию** (не считая тело `compute_y`).

Важно: если `s1 = 0` с самого начала (`N = 0`), `beqz s1, rf_end` перед циклом предотвращает вход в него — `jal` с декрементом не был бы корректным для нулевого счётчика.

## Почему .org 0x100

Бандл размером 14 байт, начавшийся с адреса 0x7E, занимает байты 0x7E–0x8B — и перекрывает IO-порт 0x80. Процессор читает из IO вместо памяти инструкций → «instruction in memory corrupted». Смещение секции на 0x100 гарантирует, что ни один бандл не пересекает диапазон 0x80–0x87.

## Почему решение оптимально в рамках VLIW-IV

1. **Минимальная глубина цепочки зависимостей.** Три слагаемых Y[i] вычисляются за 3 бандла (бандлы 1–3): параллельно `2·X[i−1]` и `lw X[i]`, параллельно `3·X[i]` и `2·X[i−1]+X[i−2]`. Сократить до 2 бандлов невозможно из-за зависимости `mul t1 = 3·t0` от свежего `t0`.

2. **Нулевые накладные расходы на возврат.** `jr ra`, запись результата и обновление истории упакованы в один бандл — выход из `compute_y` не стоит отдельных бандлов.

3. **Нет лишних загрузок.** Коэффициенты (3 и 2) и адреса портов загружаются один раз в `_start`, а не при каждом вызове `compute_y`.

4. **Счётчик цикла «бесплатен».** `addi s1, s1, -1` упакован с `jal` — декремент не занимает отдельного бандла.
